CodexのバックアップとしてAntigravityを試してみた

Codexのレート制限で作業が止まったときのために、Googleの開発エージェント「Antigravity」を予備として導入してみました。乗り換えるのではなく、困ったときの“バックアップ”として同じフォルダを編集する実験記録です。

1. きっかけはCodexのレート制限

このサイトの更新や記事の追加は、主にVS Code上でCodexにお願いして進めています。非エンジニアの私にとって、複数のファイルをまとめて確認して直してくれるCodexは本当に頼もしい存在です。

ところが先日、記事をテンポよく追加していたところ、突然ChatGPT Plusプランのレート制限（利用上限）に達してしまいました。

もちろん、少し待てば（数分から数時間経てば）再び使えるようにはなります。とはいえ、「よし、今日も作業を進めるぞ！」と集中していたタイミングで手が止まってしまうのは、なんとももったいない時間です。「Codexが休んでいる間だけ、代わりに手伝ってくれる予備のエージェントがいたら助かるのにな……」と考えたのが、今回のきっかけでした。

2. すでにGeminiに課金していたという現実的な理由

予備のAIツールを探すとなると、GitHub Copilotなど他のサービスを新しく契約する方法もあります。ですが、月額の固定費をあちこちに増やすのはできれば避けたいところです。

そこで思い出したのが、「そういえば私、GoogleのGemini系サービスにもすでに月額料金を払っているのでは？」ということでした。

Googleが提供している開発エージェント「Antigravity」なら、手持ちのGoogleアカウントの契約を活かして、追加の出費を抑えながら使える可能性があります。「乗り換える」のではなく「すでにある枠を予備として活用する」。お財布的にも無理のない、とても現実的な理由からのスタートでした。

3. Windows版Antigravityをインストール

さっそくWindows版のAntigravityをダウンロードしてPCにインストールしました。

初期設定を進めると、開発用途に合わせたプラグインを選ぶ画面が表示されました。今回はこのWebサイト制作が目的なので、「Modern Web Guidance」を選択しました。

他にもAndroidアプリ開発やFirebase、Flutterといった選択肢が並んでいましたが、今の私にはまだ必要ありません。手を広げすぎず、自分が今やっているWeb制作に直結するものだけを素直に選んで導入を完了しました。

4. VS Codeの拡張ではなく「別の開発環境」だった

ここで、初心者ならではの思い込みがありました。私は使う前まで、勝手に「VS Codeの中で、CodexからGeminiのボタンに切り替えて使うのかな？」と想像していたのです。

しかし実際に起動してみて驚きました。AntigravityはVS Codeの拡張機能ではなく、それ自体が独立した別の開発環境（IDE・別アプリ）だったのです。

「えっ、別のソフトだと今までの作業はどうなるの？」と一瞬戸惑いましたが、すぐに大切なことに気づきました。「同じローカルフォルダを開けば、編集する対象は同じ」ということです。

たとえば、このサイトのプロジェクトフォルダ（code-yomereba-ii）は、PCの中に1つだけ存在しています。それを「VS Code + Codex」から開いても、「Antigravity」から開いても、見ているファイルは全く同じ手元のフォルダです。アプリが違っても、作業机の上の同じノートを開いているようなものだと分かり、ほっと安心しました。

5. 同じフォルダだから、Git pullは必要ない

ここも非エンジニアにとって目からウロコだった、重要なポイントです。

別のアプリで作業するとなると、「GitでGitHubから変更をpull（取得）してこないといけないのかな？」と考えてしまいがちです。ですが、同じパソコン内の同じフォルダを直接編集している限り、Git pullは一切不要でした。

Antigravityがファイルを修正して保存すると、その変更はパソコン内のファイルにそのまま保存されます。そのため、VS Codeに戻って同じファイルを見るだけで、何もしなくても「変更された差分」がそのまま画面に現れます。

クラウドを経由してやり取りしているのではなく、単に同じ部屋にある同じファイルを2つのソフトで交代で見ているだけ。この感覚がつかめると、2つのツールの行き来がとてもシンプルに思えてきました。

6. 実際の運用ルール：主役はCodex、予備にAntigravity

両方の道具が揃ったところで、迷わないようにこれからの作業ルールを決めました。

  1. 普段（Codexが動くとき）：
    これまで通り「VS Code」でCodexに指示して修正する。
  2. Codexがレート制限になったとき：
    「Antigravity」を起動し、同じフォルダを開いて修正してもらい保存する。
  3. 修正が終わったら：
    Antigravityを閉じ、「VS Code」に戻る。
  4. Gitの記録と送信：
    VS Codeの画面で変更（diff）を確認し、納得できたらVS Code側でcommitとpushを行う。

Gitのcommitやpushといった履歴管理の操作は、慣れているVS Code側に一本化することにしました。こうしておけば、「どちらのツールでGit操作をしたっけ？」と混乱することもありません。

7. 最初にやらせたこと：「このサイトの構成を説明して」

Antigravityを立ち上げてプロジェクトフォルダを開いたあと、いきなりファイルの修正を頼むのは少し不安でした。そこで最初に、こんなお願いをしてみました。

「このプロジェクトの構成を確認して、既存ファイルは変更せず、サイトの目的と主要フォルダ構成だけ説明してください」

するとAntigravityは、ファイルを一切勝手に書き換えることなく、以下のような構成を的確に答えてくれました。

  • 非エンジニア向けの入門サイトであること（README.mdの内容）
  • トップページや記事が入ったarticlesフォルダ
  • カテゴリ一覧をまとめたcategoriesフォルダ
  • 用語やコードを調べるindexesフォルダ
  • スタイルシートや画像が置かれたassetsフォルダ
  • PWA用設定のmanifest.webmanifest

プロジェクトの全体像をスラスラと説明する姿を見て、「あ、この子もしっかりサイト全体を読めているな」と確認できました。まずは“読む力”があるかをテストしてみる。これは新しいAIツールを試すときの安心な第一歩だと感じます。

8. Codexの代わりになるのか？ バックアップとしての価値

では、AntigravityはCodexの完全な代わりになるのでしょうか？

正直なところ、現時点では「まだ分からないし、焦って比べる必要もない」というのが私の率直な感想です。私はすでにCodexの操作感に慣れていますし、これまでの修正品質にも十分に満足しています。Antigravityがどこまで細かなニュアンスを汲み取ってくれるかは、これから実際に使いながら確かめていく予定です。

ただひとつ言えるのは、「Codexが止まったときに作業を止めずに済むバックアップがある」というだけで、大きな価値があるということです。

しかも、もしAntigravityの修正が思うようにいかなければ、その変更をGitでcommitせずに元に戻し、Codexの制限が解除されたあとにCodexでやり直せばいいだけです。ローカルのGitがあるからこそ、失敗を恐れずに予備ツールを試すことができます。

9. AI開発では「1つのツールに依存しすぎない」方が気が楽

今回の体験を通じて、AIを使った開発では「特定の1つのサービスに依存しすぎない体制」が意外と便利かもしれないと感じました。

  • 全体の相談や方針決め：ChatGPT
  • 普段のメイン作業：VS Code + Codex
  • レート制限時の予備・補佐：Google Antigravity

もちろん、最初からたくさんのツールを同時に使い分けると頭がパンクしてしまいます。だからこそ、「主役はあくまでCodex、Antigravityは困ったときの頼れる控え選手」というシンプルな位置づけにしておくのが、初心者にはちょうどいい距離感です。

10. この記事自体をAntigravityで作ってみた

せっかく予備の開発環境を整えたので、この記事の初稿の作成とサイトへの追加作業は、実際にAntigravityにお願いして行いました。

「CodexのバックアップとしてAntigravityを試す」という記事を、当のAntigravity自身に作ってもらう。ちょっとした実験気分でしたが、サイトのルールに従って見出しを整理し、他のHTMLとのリンクもスムーズにつなげてくれました。これなら、いざCodexが休憩に入っても、安心して留守を任せられそうです。

今日覚えること

同じローカルフォルダを開けば、VS CodeでもAntigravityでも編集対象は同じ。pull不要で差分を確認できます。

「主役はいつものAI、止まったら予備のAI」。バックアップを1つ持っておくと、開発が止まらず安心です。
